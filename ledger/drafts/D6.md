# D6 — Engineering isn't in discovery

## Risk
Statement: Engineering isn't in discovery. Feasibility risk is deferred and surfaces late, in build.
Category: Feasibility
Gate: Run
Area: Discovery

## Assumption(s)
### A1
Statement: We believe that if an engineer is in the room for the last discovery review, at least two feasibility fails will be named before build that three non-engineers in the same review will not name.
Success criteria: Same packet. Engineer list has ≥2 feasibility blocks (cannot build as written, missing constraint, unsafe). The three non-engineer lists together miss at least two of those. All four people see the same packet.
Failure criteria: Engineer adds no feasibility block. Or non-engineers already named the same blocks (then "engineering isn't in discovery" is not what failed this sample).

## Slice(s)
### S1 (tests A1)
Method: One existing discovery packet (same unknown as D1). One engineer, three non-engineers. Silent lists of "what would break in build." Then compare. Do not run a build. Do not invent a product. If no engineer is available, stop and mark that as unknown — do not role-play an engineer.
Type: Feasibility
Execution: Requires manual run
Scope / time-box: 4 people. 30 minutes. One packet.

## Signal

Failure signal: No extra blocks from engineering, or everyone already saw them.
Threshold: Fail on "no extra blocks" → putting an engineer in the review did not change the risk picture; look at the packet, not the seat. Pass → missing engineering in discovery would have hidden real build breaks in this sample. Do not start a full dual-track process off this one review.
